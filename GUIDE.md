# Lodestar — the reference

Lode is **right ⌘** (configurable in `~/.config/lodestar/lodestar.json`).

## Chains are sticky, on purpose

Once a traversal starts (`lode W`, `lode '`, …) it waits **indefinitely** — the gesture is identical whether you finish it in 80ms or after a phone call. The glass guide panel stays on screen the whole time showing your prefix and every legal continuation (with app icons); a wrong letter keeps you in place with a note rather than ejecting you. Only a completion or `esc` ends the chain. While a chain is active, stray keystrokes are swallowed (they never leak into the focused app). And holding lode by itself for half a second peeks the top-level guide — the system teaches its own map.

The guide also fades as you learn: over a subtree whose every address has compiled, the map waits up to two seconds before painting, so recall gets its chance before reading does — and one wrong key or abandoned chain brings it back immediately for an hour. A fluent chain never sees it. `guide.fade: false` paints it immediately, always.

## Launcher ranking & teaching

Results are ranked by fuzzy match quality **plus frecency** — every summon (graph, launcher) counts toward the app's score, decayed by recency. An empty query shows the things you actually go to, most-used first. Rows carry teaching chips: an app with a graph address shows it (`E P` on Proton Mail), a running app with several windows shows `⇥ 3` (Tab expands it) — every search is a flashcard for the faster gesture. The window chooser lists most-recently-focused first, with the window you're already in last; `esc` walks back to apps when you arrived via Tab. Row views are cached — typing repaints, never rebuilds. Guide columns adapt to your screen (a laptop gets two, a big display three or four), and flashes wear the icon of the app they acted on.

**`⌘K` on a browser row speaks profile.** The add card carries a Profile row — `⇥` opens the list, a digit picks, `0` is **Inherit**, the bare app that opens whatever the browser opened last — so `lode B P` and `lode B W` can be different Braves. Bindings conflict on target, never on app: three chains can mean Brave so long as each opens a different profile, inherit counting as its own, and the card refuses a duplicate by naming the address that already means it. The browser's existing bindings all appear on its card, each wearing the profile it opens, and a browser keeps offering **a — Add to graph** until the bare app and every profile are spoken for.

## Breath mechanics

- Bound paths are prefix-free automatically (a path resolves the instant it matches, so nothing deeper can ever be created past it — and binding a prefix of an existing path is refused as shadowing).
- `⇧letter` on an existing path overwrites that snapshot.
- Delete is verb-before-noun: `⌫` inside the chain arms deletion (the guide shows it), then the path you type is deleted instead of visited. `⌫` again disarms.

## Multiple monitors

**Every monitor owns its own layout** — members, orientation, digit indexes. Your verbs act on the _active_ display: **the one under the pointer** by default, so where your mouse rests is where summons land and panels appear (`app.active-display: focus` switches to the keyboard-focus display instead). Summons follow **visit-don't-pull**: a target already visible on _another_ monitor is focused where it lives (its arrangement untouched); anything hidden, parked, or freshly launched materializes on the screen you're using; on the _same_ monitor, a plain summon still goes maximized as always. A plain summon also **sweeps its own strays**: any window Lodestar placed this session that is still standing on the active display parks with it, so the resting posture — one app, maximized — is true of the screen and not just the layout (welcome news behind a transparent terminal). Windows macOS placed are never touched; adopt one with `lode 0` and it joins the system. One `lode ←` restores the whole stage, and reaching any parked window by an outside road — cmd-tab, the Dock — brings it back where it was. `lode [`/`]` throw the focused window to the neighboring display (physical order, wrapping) — plain arrives maximized there, `⇧` arrives beside. Undo is one global timeline across displays; breaths capture the whole multi-display world and restore members to their original monitors (or the active one if that monitor is unplugged); peek badges index the active display.

**Docking just works.** Unplug a monitor and its members quietly park — the surviving display's arrangement is untouched — while the departed arrangement is remembered by the monitor's hardware identity (not its session ID, which macOS can reassign). Plug the same monitor back in and the arrangement returns exactly, minus anything you deliberately re-placed while undocked: your placement always wins, a world-moved-on guard. The memory is per-session on purpose — a Lodestar restart while undocked starts fresh, and breaths are how you bring back a world deliberately.

## Windows you did not summon

**They are left alone.** A window born outside Lodestar — a launcher, the Dock, `⌘N`, a certificate prompt, a file reveal — floats untouched above your layout, exactly as macOS would have it, and never hides what you were reading. System and accessibility floaters (notch apps, Control Center, overlay slivers) belong to accessory processes the model never even tracks.

**`lode 0` makes the focused window fill the display** when you want it managed: the summon treatment on demand, everything already in the layout parked, `⇧0` to join beside instead. It also **enrols** the window, so from then on it answers to `lode 1…9`, breaths, orientation flips, and `lode ←` like anything Lodestar summoned. That is the only way an unmanaged window becomes managed — Lodestar never decides on its own that a new window is a destination, and nothing is ever parked except what a placement displaced.

## The clipboard

`⇧⌘V` opens the paste strip: **recents along the bottom** labelled by the home row, left to right, `A` through `;` as far as the display has room for, and **pins climbing the left edge** numbered 1 to 5. Both of the things you are most likely to want — a pin, or what you just copied — sit at the same corner, so there is one place to look.

- **A letter pastes it as plain text.** Most pasting is unformatted and that is the good default.
- **`⇧letter` pastes it as copied** — rich text, HTML, or whatever proprietary flavour the source app offered. An image has no plain form, so both paste the image.
- **`⌘letter` opens that card's actions**: pin or unpin, delete, or never save from that app again. A text card offers `E` to edit it; an image offers `E` to view it and `S` to save it.
- **`E` on an image opens it across the display**, fitted whole, the strip gone beneath it. Pinch to zoom and pan with two fingers, as with any image, or from the keys: `H` `J` `K` `L` slide the picture, shifted three times as far as in scroll mode, and `+` and `-` zoom; nothing is clicked. It is the one surface that takes focus, because a pinch only reaches the active app, and it hands focus back to the app it took it from when it closes. `esc` or `⏎` steps back to the strip; `S` goes on to save it.
- **`S` on an image saves it under a name you edit.** The band opens with a name already in it, made from where the image came from and when, like a screenshot's, so `⏎` alone is enough. The caret stands at its end: `⌫` edits it, `⌥⌫` takes a word, `⌘⌫` clears it for a name of your own. A slash inside the name is a subfolder, a name starting with `/` or `~` is a path of its own, a trailing slash is a folder that takes the offered name, and `.jpg` or `.tiff` writes that format instead of PNG. Everything else lands in `clipboard.save-to`, which is Downloads unless you say otherwise. `esc` steps back with nothing written.
- **`1`…`5` reach the pins.** Slots are permanent: a new pin takes the lowest free one, and unpinning leaves a hole rather than renumbering the others, so a pin you have learned never moves. Empty slots still draw, so the numbers are always visible.
- **`/` searches**, `↵` pastes the match, `esc` steps back to the strip. A second `esc` closes. Everything your keyboard types is a search character — hyphens, underscores, slashes, dots — because that is what file names and commands are made of.
- **`⌥letter` pastes a match without leaving the search.** While you are typing, the letters belong to the query, so the cards wear `⌥` on their chips to say what addresses them: `⌥` and a chip pastes that card, `⌥⇧` pastes it as copied, `⌥⌘` opens its actions, and `⌥1`…`⌥5` still reach the pins. `←` `→` walk the matches for the hand that would rather not reach.
- **`⌘V` pastes into the search.** The pasteboard's text, folded to one line, joins the query; with the strip open and no search yet, `⌘V` opens one with that text. The same `⌘V` works in the launcher, the commands bar, Ask, select and click hints.
- Any lode gesture exits and executes, the same as scroll and hints.

**Images are found by what they show.** A screenshot is read once, a beat after it lands, and the text becomes part of its card's search — a screenshot of an error message is found by the error. **Browser copies carry their page.** The card shows the host it was copied on beside the app icon, and the search reads it, so `github` finds the clips you copied on GitHub.

**A copy of several things stays several things.** Three files selected in Finder go on the clipboard as three items, and they arrive in the history as one card marked `3 files` that pastes all three. The card reads by name, so the search finds them the way you would look for them. A copy past thirty two items is left alone entirely rather than kept in part.

Pasting sets your system clipboard, so plain `⌘V` repeats it. What it never does is **reorder the list** — copies reorder, pastes do not, so the strip stays your copy history and the positions hold still while you use them.

**What is never recorded**: anything a password manager marks concealed, transient, or auto-generated; anything from an app in `clipboard.exclude-apps`; and anything containing a substring in `clipboard.exclude` — which is how you keep a reel you are forwarding out of your history without banning your browser. History lives in `~/.local/share/lodestar/clipboard`, never in `~/.config`, because that directory ends up in dotfiles repositories. It is **encrypted on disk** (see "The clipboard history, sealed" below), excluded from backups and readable only by you. `clipboard.max-size-mb` decides how far back it reaches; pins are never trimmed. `lodestar clipboard clear` erases it, pins included, and destroys its key.

In a password field macOS blocks synthetic keystrokes outright, so Lodestar puts the clip on the clipboard and tells you to press `⌘V` yourself rather than failing silently.

## Scroll mode

`` lode `  `` toggles it (Escape closes too). Entry warps the pointer to the focused window's center — the same gesture scrolls the same thing every time. **The mode wears the pill**: one floating pill that every lens shares, the mode's symbol and name on its left wing, the app's name and icon on its right. When a lens is listening for typing a still caret stands between the wings, and the moment you have typed anything both wings fold to their glyphs and your letters take the middle; the symbol and the icon never move. A capital is a pick, not a search, so it never appears there: the chips it narrows show it instead, the letters already typed in the accent and the chips it can no longer reach gone. In select, once the start anchor lands, the anchored word rides ahead of the far end's search between the wings, so the stage is legible without a sentence. The pill can be dragged by its glass, and comes back where you left it for the rest of the session. **`lode ?` inside any lens** shows every key that lens owns: the pill grows into a card with the keys above its row, and `esc` folds it back with the lens still up. The same chord inside the launcher, Ask or the commands bar grows the bar to hold its keys beneath its rows, and inside the clipboard strip or the settings window shows that surface's keys on a sheet; no surface carries a legend of its own, and a plain `?` is only ever a character. **`/` aims anywhere else**: it opens the same band as `lode /`, you type a few characters of a word you can see in the pane you want, and the pick lands the pointer on that word; the wheel goes to whatever scrolls under it, so a sidebar, a thread pane, a table, or a header that scrolls sideways is addressed by what is painted in it, in a web view or a native window alike. Uniqueness commits, so `/thr` lands on the one word that starts that way without a capital; several matches wear capital chips. Nothing is clicked, focused, or copied: the pointer moves, and that is the whole verb. `esc` in the band steps back to scroll mode with the aim unchanged. The read covers the whole display, so the word can be in the window beside the focused one: the pointer lands there and that window scrolls without taking focus, which the trackpad cannot do without a click. (`⇥` used to cycle the panes the accessibility tree named; it was retired when the measurement said the tree names none in a browser or an Electron app.) **A click or a swipe of your own ends the mode**: the hand reaching for the pointer is the end of the lens, and a mode left up would swallow the typing after the click. **Holding `j/k/h/l` scrolls at constant velocity and stops the instant you release** (`scroll.smooth`, with `scroll.speed` px/s; turn smooth off for classic one-step-per-repeat with `scroll.step`). **Shift means more**: `⇧J/K/H/L` move three times as fast (press or release shift mid-hold and the velocity follows), and `⇧D/⇧U` move a full page instead of half. `gg`/`⇧G` jump by setting the pane's scrollbar value directly — instant and app-independent — with `gg` a true two-tap, no timeout; `0`/`$` are the same jumps to the left and right edges, for a board or a wide table the aim reached. Polarity follows your system natural-scrolling preference automatically. Scroll mode is a lens, not a transaction: **any other lode verb exits and executes immediately** (`lode S` mid-scroll just takes you to Slack); plain typing is swallowed while the mode is on.

## Click hints

`lode ;` is select's machine wearing the click verb: same capture, same pixel sensor, same grammar, and the door you entered through decides what a capital does. **Lowercase always aims** — type a few characters of anything you can read, matches highlight and wear capital chips — and **a capital always fires**: `⇧letter` clicks the word you picked, `⌃⇧letter` right-clicks it (the element's own context-menu action when the tree knows it, a synthetic right-click at the word otherwise; on a two-letter chip, the last key decides the button). Because the sensor is the screen itself, this works identically in a terminal, a browser, an Electron app, or anything else with visible text — clickability is not asked of the app, it is declared by your pick.

Before you type, the elements the accessibility tree _can_ name — buttons, links, checkboxes, text inputs — wear corner-pinned chips immediately, so a dialog's three buttons cost one capital with no typing at all, and icon-only controls stay reachable. Typing hands the glass to the search universe; backspacing to nothing hands it back. Wherever your pick lands inside a tree-known element, the click is the app's own press rather than a synthetic one; text inputs focus, putting your typing there.

`lode ⇧;` is the **chain-click lens**: every fire re-captures and relabels after a beat, so a click that changed the app — opened a panel, revealed a menu — gets a fresh read. Filling a form or clicking through a wizard never leaves the mode. Same exit rules as scroll: `esc` (or `lode ;` again) closes, any other lode verb exits and executes.

The tree harvest stays asynchronous and bounded — a heavy Chromium page can never stall the overlay — and Electron apps get `AXManualAccessibility` woken automatically. The first `lode ;` may ask for Screen Recording, the same permission select already earned; until granted, the tree-named chips still answer.

## Select (`lode /`)

Text is the mouse's last stronghold: you can reach any window without it, and then you drag to select three words. `lode /` ends that. Text needs no assigned address, because it is made of the characters your keyboard already produces — **you type a few characters of what you can see**, every match on screen highlights and wears a capital chip, and **`⇧letter` picks one as the start of your selection**. The pick lights up the whole word, and from there you have two ways out: **`⌘C` takes just that word** and the mode is done, or you type again for the far end — pick, and the selection spans from one anchor to the other, whichever order you placed them, and the mode is gone.

The far end can be anywhere you can see, **including lines below the one you started on** and text in a window beside it. The span then runs the way reading does: the rest of the line you anchored in, everything between it and the far end, and the far end's line up to the word you picked — every piece of it highlighted, so what lights up is exactly what `⌘C` gives you. Between means between on the page: the span runs down the column your two anchors share, so a sidebar or a neighboring card beside it stays out of the copy. Anchor in one column and end in another, and it takes both.

Lowercase always searches; capitals always pick — and shift is the door, not a hold: on a two letter chip, only the first letter needs it, since once a label is underway every further letter can only be finishing it. A single character query matches only standalone words, so `i` finds the word "I" rather than every letter i on screen. There is no timeout and no ambiguity: `$`, digits, spaces, and shifted symbols are all search characters (labels are letters only), so `$100` or a two word phrase types exactly as seen, and matching is case-insensitive so you never reach for a real capital. The span snaps to word boundaries — two typed characters name a word, they do not dissect it, so `fo` means through "fox" and a URL or identifier comes out whole. `⌫` walks back — the label, then the query, then the start anchor itself. `esc` clears, as everywhere.

Select reads the screen itself: a capture of the focused window, recognized by the system's Vision framework, so it behaves identically in a terminal, a browser, a chat history, or anything else with visible text. The first `lode /` asks for the Screen Recording permission (grant it in System Settings, then quit and reopen Lodestar); until then, and for anyone who declines, an accessibility-based fallback covers what it can.

What leaves the clipboard is read twice. The pixels are served at once; then the app is asked to select the same span by a short synthetic drag and copy it, and its text stands when it agrees with the pixels up to the glyphs recognition confuses (`1` `l`, `0` `O`), in which case the app's own highlight is the ending. The drag never lands on a control. Where the app cannot select, the span is read again from the frozen frame, upscaled, and served.

The mode always ends the same way: **the span is highlighted, and the next verb is yours.** When the span is one stretch inside the text field you are editing, it becomes a real selection — the app's own highlight, so copy, replace, and delete all work from muscle memory. Everywhere else, Lodestar holds the highlight itself: it stays on screen after the mode ends, **`⌘C` copies it** (into the clipboard history like any copy), and any other key, click, or `esc` dismisses it. Copied text is checked against what accessibility could read of the same region, so a recognized `1` that was really an `l` comes out corrected — what you paste is what was there, not what the pixels resembled.

If a span is always a copy for you, say so once: **`select.copy-on-complete`** serves the clipboard the moment the second anchor lands, in every ending alike, with a quiet "copied" on the band as the receipt. The highlight stands exactly as before and `⌘C` still works; the keystroke just stopped being necessary. With it on, `esc` after only the first anchor copies that word, the same ending `⌘C` reaches. Off by default — the decision lives in the config, never in the mode.

## Ask

`lode ⏎` — a second bar with its own grammar: everything typed here is a destination on the web. **Links** (`web.links`) are named sites, optionally pinned to a profile — type `yt`, hit `↵`, land in YouTube in your Google profile. **Bare domains** (anything with a dot) route by `web.routes` — case-insensitive, on whole labels, longest match wins — so `app.acme.dev` opens in your Work profile without being listed anywhere. **Anything else is a web search** (`web.search-url`), and routes apply to queries too, on whole words: searching "acme deploy" lands in the Work profile. Unrouted input opens in `web.fallback` — `most-recent` (the profile of your most recently focused browser window) or a pinned profile. Every row wears the profile it will open in as a chip; `⇧↵` opens beside. Chromium family (Brave, Chrome, Edge) for now.

**`⌘K` promotes the row you are looking at**, the way the launcher's `⌘K` promotes an app into the graph. The row decides what is on offer, and the two promotions answer different questions — _this site, by this name_ and _every link like this one, from anywhere_:

- **`a` Add link** (bare-domain rows) — the card opens with a name prefilled from the host (`youtube.com` → `youtube`); type to replace it, `↵` writes it into `web.links`.
- **`r` Route this host** (domain and link rows) — the pattern is prefilled with the whole host and the profile is seeded with wherever that destination already goes. `↵` writes it into `web.routes`, and from then on anything matching that pattern lands in that profile: paste a friend's `x.com` link and it opens in Personal, not Work.
- **`r` Route this search** (search rows) — routes match _what you typed_, not just hosts, so a search is something to route even though it is nothing to name. The pattern is prefilled with the query's first word (`acme deploy` → `acme`), since the whole phrase as a pattern would match almost nothing. A search row is the one place `⌘K` offers no link: there is no site to point a name at, and the card says so.
- **`d` Remove link** (link rows) — takes it back out; the emptied table is pruned rather than left as a husk.

The profile is a **row inside the card** — its label, its current value, and `⇥` sitting where every other key sits — rather than a hint in the footer, so it looks like the control it is. `⇥` opens a second card, one column further out, listing the profile registry on digits. For a link, `0` leaves it **unpinned** — the default and usually the right answer: an unpinned link carries no `profile` key at all, so it keeps resolving through your routes and fallback instead of freezing today's answer into the file. A route has no `0`, because a route has to name a profile.

The card always says _why_ a destination opens where it does — `opens in Work · pinned`, `· matched acme`, `· fallback`, `· most recent browser` — so an inferred answer is never mistaken for one you chose. You never type a scheme (`https://` for the web, `http://` for a dev server — see below), and a name or pattern already in use is refused with what it points at rather than overwritten. The new row appearing in the bar, wearing its profile, is the receipt.

**Dev servers are destinations, not searches.** `localhost:3000`, `box.local`, `app.test/login`, `192.168.1.5:8080` all resolve as places to go — a port counts the same as a dot — and they open over `http://`, because a machine on your desk has no certificate and `https` would be the one guess that could never work. Loopback, `.local`/`.localhost`/`.test`/`.internal`, and the private IPv4 ranges get that treatment; everything else is still the web. An explicit scheme is never second-guessed.

## Links clicked in other apps

Routes only help where Lodestar is asked, which is the half of the problem that needs it least: when you type into the bar you already have the chance to choose. The clicked link is the case where you have none. So Lodestar can stand as the http handler and apply the same `web.routes` to links clicked anywhere — a friend's `x.com` link opening in Personal rather than whatever profile happened to be frontmost.

**Nothing changes until you choose it.** The menu bar offers _Route Clicked Links Through Lodestar_; it records whatever your default browser is right now, asks macOS to hand over the role (macOS puts up its own confirmation panel — that is the real gate), and remembers both. The same item then reads _Give Links Back to Brave_ and puts it back.

**The point is invisibility.** A link that matches no rule goes to your saved browser, untouched, brought forward exactly as a click always did: no rewriting of the URL, no `web.fallback`, no most-recent-profile guessing, and **no placement** — a link someone sent you is not a request to rearrange your layout. Only a matched rule diverts, and only then is a profile launch paid for. Measured cost of the decision itself is about 20µs; the budget for the whole hop is invisibility, and it is a tested ceiling rather than a hope.

**It fails safe, deliberately.** `web.clicks.enabled: false` while still registered makes Lodestar a transparent pass-through, so the off switch works from a text file without a trip through System Settings. A rule naming a deleted profile passes through rather than stranding the link. Uninstalling restores your saved browser before removing the app. And while Lodestar holds the role, an auto-update has to prove its router answers before the watchdog blesses it — booting is not enough when every link on the machine depends on you.

A profile is referenced by naming it: `browser:Name` (`brave:Work`, `chrome:Personal`), the same form everywhere — routes, links, the fallback, meeting calendars, and the graph. There is no registry to maintain; the browser's own profile list is the authority, and every reference is checked against it at Reload Config — a renamed browser profile surfaces as one flagged line naming the exact config path, not a mystery failure later.

## Meetings

The calendar's next join, offered at the door. Off by default: turn it on in Settings (`lode ,` then 7, Meetings), which shows one card and then macOS's calendar-access prompt — the permission is asked when you reach for the feature, never at install. Once on, a card in Lodestar's voice appears `meetings.lead-minutes` before a meeting starts (default 5) — the meeting as a sentence, counting minutes, then seconds, then that it is beginning — and lives the meeting out, so joining late is one gesture too. **Tap lode twice to join. `lode ⌫` dismisses this occurrence** — a recurring meeting returns tomorrow; a chip you joined or dismissed never resurrects, even across a restart. Declined and all-day events never get a chip, overlapping meetings queue soonest-first, and a join through the chip spends it.

The link is sniffed from the event's URL, location, and notes (Google Calendar's Meet links live in the notes; EventKit never sees the conference field). Zoom and Teams join natively when the app is installed — the URL is transformed and handed to the app by name, never a bare LaunchServices open. Everything else joins in a browser profile, resolved by precedence: **`meetings.calendars` first** (calendar name, then account name → profile — the calendar is the only signal that can tell two meetings on the same host apart), then `web.routes`, then the ordinary fallback chain. The chip wears the profile and which rule chose it.

The coach learns to offer this feature itself: manual joins (meeting hosts opened, focus landing on Zoom or Teams) are already in the observation ledger, and when the habit is steady the offer appears seconds after a join — accept writes exactly the one line `meetings.enabled: true`. The observation layer keeps the provider and the deciding rule per chip, never a title, attendee, or URL.

## What Lodestar notices

Lodestar observes in two records, on this machine only, each with its own switch. The **logbook** is how you move between apps, windows and gestures, and the coach reads it; `observations.logbook` turns it off, and off means nothing is recorded and no file is written. **Health** is the rhythm of your hands (when each key goes down and how long it is held, by hand, finger and kind of key, with no key's identity stored) and the pointer's motion; `observations.health` turns it off, independently of the logbook. `observations.logbook-mb` bounds the logbook (256 MB by default, 64 at least; its oldest months leave first), and `observations.health-mb` is the size at which Lodestar tells you the health record is nearing it (1 GB by default, 256 MB at least; health is never deleted on its own).

The rule is **how you got places, never what you were doing there**. It records the pauses inside an address, whether the map was consulted, chains abandoned and the key the hand pressed instead, which road reached an app and what that road cost in seconds, which app tends to follow which, and the host a destination opened at — the routing fact, so a repeated habit can become one config line. It never records a window title, a URL's path or query, a clipboard, or what you typed into the launcher beyond its first two characters. Everything lives in `~/.local/share/lodestar/` — `events.jsonl`, a rolling year of raw material sharded by month, and `observations.json`, the running summary — deliberately not in `~/.config`, which is what people commit to dotfiles repositories. Nothing ever leaves the machine.

With `observations.health` (on by default, its own switch because it watches more than Lodestar's gestures) the record also keeps a pulse of the hands: keystrokes and clicks counted, scrolling counted as reaches, active minutes, typing rhythm, and the backspace rate — the early strain signal. Beneath the pulse is the raw record, one row per press: when it went down, how long it was held, which hand and finger, and what kind of key it was (a letter, a digit, space, punctuation, a modifier). No key's identity is stored. That is not the same as none being recoverable. Hand, finger and kind sort the letters into eight groups, with spaces marking where words end, the way a phone keypad sorts them; against a list of 44,000 common words, two in three have a sequence no other word shares, and nine in ten of those six letters or longer. So what was typed can be partly reconstructed from the raw record. That is why it stays on this machine, and why any export is a separate step you consent to after seeing what it contains. The health record is included in Time Machine backups, because it is a baseline nothing can recompute; the logbook is not. Both are sealed at rest, below.

The record also says when it could not see, so a quiet stretch is never mistaken for rest: while a password field held secure input, while the keyboard tap was off or accessibility was gone, while health was switched off, while Lodestar was not running, and while the Mac slept. Each span keeps its kind, its start and its end, and nothing else; never which app held secure input. Secure input has no notification, so it is checked every two seconds, and its spans are good to within two seconds at each end. `lodestar observations` shows how long the instrument was blind over the last four weeks, and why.

Each press is charged to the keyboard that sent it when Lodestar can tell, by the keyboard type the press carries and whether the lid is closed, and to no keyboard when two could have sent it. `health.exact-keyboards` (Exact Keyboard under Health in Settings, off by default) tells it exactly: Lodestar listens to the keyboards' own reports and charges each press to the one whose report matches it in time. That needs Input Monitoring in Privacy & Security, which Lodestar asks for only when you turn this on. Which key a report was is compared in memory to make the match and is never stored or logged. A press that no single keyboard's report matches (one a remapper rewrote, or the same key on two boards at once) falls back to the usual attribution. Clicks are also kept per app with the clicked control's role class (button, link, text field) and whether the hand had just left the keys for it — an app name and a role, never a label, a title, a coordinate, or a URL. The report shows the mirror and never judges it.

Two measurements still do most of the work, and neither needs to guess at what you would have done otherwise. **Pauses**: an address you own is typed at motor speed, one you are reconstructing has a gap in it, which is as close to "has this become muscle memory" as you can get without asking. **Abandons**: a chain you started and escaped out of is unambiguous in a way a slow chain is not, because a slow chain might be a phone call. Anything over ten seconds is discarded rather than averaged, since chains wait indefinitely by design and one interruption would otherwise poison every number here.

`lodestar observations` prints all of it, plainly, because a store you cannot read is one you cannot consent to; `lodestar observations clear` deletes it, both records at once, or one with `--habits` (what the coach reads) or `--health` (the health record). What the report is willing to conclude is gated twice: a finding must be probably worth more time than it costs — relearning included, priced from your own learning curves — and it must survive false-discovery control across everything else being tested. Silence stays the honest answer until then, which is most of the first weeks. `lodestar observations engine` shows the fitted models behind the verdicts, for eyes that want the working shown.

### Sealed at rest

The health record, the logbook, the clipboard history and the state file are encrypted on disk: AES-256-GCM, which also authenticates, so a file that is altered, moved or swapped does not open instead of opening as something else. Each is a record with a key of its own. The keys live in your **login keychain** (service `com.vaccone.lodestar`), never beside the files, so a copied folder, a sync service, a disk image, or another app reading your home directory holds ciphertext. What this does not do: it does not stop code running as you (it can ask the keychain), it does not hide that a file exists, how large it is, or when it was written, and it is no substitute for FileVault.

What is sealed: the raw press and pointer record (`keys/` and `pointer/`, one sealed journal per day, `keys-YYYY-MM-DD.sj`), the health log and its monthly archive, the era fingerprint and the span ledger (`blind.json`) with the health key; the logbook's ring (`events*.sj`), `observations.json` and `rollups.json` with the logbook key. `install-id` is not part of this. The state file (below) and the clipboard history (its own section further down) are sealed too, each under a key of its own. Files are `0600` and `keys/` and `pointer/` are `0700`.

**When the key cannot be had, nothing is guessed.** If the keychain is locked, or refuses (a build signed differently from the one that made the key is asked about it, and you may say no), the record is paused for that launch: nothing is read, written, deleted or migrated, the log says so once, and it tries again at the next launch, and when the screen unlocks if the keychain was only locked. While the health record is paused, presses are dropped as they are when health is off, and if the key returns while Lodestar is still running (the screen unlocking) the record says why it has a gap (a `key unavailable` span in the blind ledger); a launch that never gets the key leaves the gap to be written at the next start as time not running. If the key is truly gone while sealed files exist (a restore without the keychain, an item deleted in Keychain Access) the health record is refused: nothing is deleted, `lodestar diagnose` and Settings → Observations say the key is gone, and **Start a new health record** moves the unreadable files into a dated `health-unreadable-YYYY-MM-DD/` folder beside them (never deleted) and begins again. That is never automatic. The logbook is derived behavioral data, so with its key gone its unreadable files are moved aside the same way (`logbook-unreadable-…`), a new logbook starts, and `diagnose` says so. Deleting the health record or the logbook destroys its key as the last step, so what a disk still holds of the deleted files is noise.

**Your files from before this version** are sealed in the background after launch, one file at a time. Each is written sealed, read back, compared with the original, and only then is the original removed; interrupted at any moment, the next launch finishes it, and a build older than this one that writes new plaintext for the same day or month has it merged in rather than overwriting anything. `lodestar diagnose` says how far it has got (`health record: sealed, N days; migrating M files`) and whether everything that is sealed opens.

**Two things the migration cannot do.** Deleting a plaintext file does not erase its blocks on an SSD or under APFS: until the system reuses them, the old bytes may be recoverable from the disk. And Time Machine backups taken before this version still hold the plaintext health files (they are backed up on purpose); backups taken from now on hold only sealed files. The key travels with the login keychain, which Time Machine and Migration Assistant carry, protected by your login password: so a backup of the whole Mac restores a readable record, and a copy of just the folder does not.

**Your own scripts** keep working through an export, which decrypts to the formats the record was kept in:

```sh
lodestar health export ~/health-export              # keys/, pointer/, health-events*.jsonl, health-*.jsonl.z, era.json, blind.json
lodestar health export ~/logbook-export --logbook   # events*.jsonl, observations.json, rollups.json
```

It writes into a new or empty folder, files `0600`, prints every file it wrote, and says plainly which it could not read (a locked keychain is "the key is unavailable", never an empty file). A day file is a segment's header and rows: `keys-DAY.bin` for the day still open and `keys-DAY.N.bin.z` for a closed one, whose bytes are raw DEFLATE (the Compression framework's zlib), which Python reads with `zlib.decompress(data, -15)`. The header is 64 bytes and a roster, then 24-byte little-endian rows for presses (microseconds since the epoch, microseconds held, hand, kind, flags, keyboard type, finger, modifiers, how many keys a modifier covered, roster keyboard, lid); `KeyStore.swift` describes every byte. The export is plaintext on your disk, so it is yours to keep somewhere you trust and to delete.

### The clipboard history, sealed

What you copy is the most sensitive thing Lodestar keeps, so the history is encrypted at rest with the same primitives and a third key, the `clipboard` ring, in the same login keychain. It lives in `~/.local/share/lodestar/clipboard/v2/`:

- `index.sj` is the index, a sealed journal of small records (a copy, a keepsake, a caption, a delete): a copy appends a few hundred bytes instead of rewriting the whole index. Every so often (past about 500 records, or twice the size of its snapshot, at idle) the log is folded into a snapshot.
- `items/<name>` is one sealed file per clip holding everything the copy brought (every item and every form of it), and `thumbs/<name>` its thumbnail. Each is sealed under **a key of its own**, which exists only inside the sealed index records, and the name is 16 random bytes: no file name says what is in it, and rotating the ring rewrites none of the blobs.

**A deletion is real two seconds later.** Deleting a clip (or a trim, or an edit that replaces it) unlinks its file at once, and then folds the log and rotates the ring's key: the old records, and the key to the clip that was in one of them, can no longer be opened by anyone, so the bytes the disk may still hold are noise. Quitting finishes a deletion that is still waiting. `lodestar clipboard clear` (and Settings, Clear history) removes everything and destroys the ring; the next copy makes a new one.

**What each state of the key does.** The ring is there: the history opens, in the background, after launch. The strip says "clipboard history is opening" for the moment that takes, and a copy made meanwhile is kept and applied when it has. The keychain cannot be asked (locked, or it refused): the history is **paused for that launch**: nothing is captured, read, written, deleted or migrated, the strip says "clipboard history is unavailable", and a keychain that was only locked is asked again when the screen unlocks. The ring is gone and sealed history exists: it cannot be read, so it is moved (never deleted) into `clipboard/clipboard-unreadable-YYYY-MM-DD/`, a new history starts, and you are told once (a flash, the log, and `lodestar diagnose`). Clearing the history while it is paused is refused rather than half done.

**Your history from before this version** is taken in at the first launch, in the background, before it is shown: each clip is sealed under a fresh key, written to disk, read back and compared with the original, and only then is the plaintext (`index.json`, `items/`, `thumbs/`, and any `index.json.corrupt-*` an older build set aside) removed, the index last. Interrupted at any moment, the next launch redoes it or finishes it, and `lodestar diagnose` says what is left. A clip whose old files were missing keeps its card with what could be read. A build older than this one that you run again writes a plaintext history beside the sealed one; the next launch of this one merges it in, by age (the newer copy of a clip wins), keeping a keepsake's place only if that place is free, and removes it.

**`~/.local/share/lodestar/clipboard` has never been in Time Machine**: the folder carries the backup-exclusion flag, set again at every launch, so backups never held the plaintext history and do not hold the sealed one. The ring is in your login keychain, which they do carry. The one thing the migration cannot do is erase: deleting a plaintext file does not wipe its blocks on an SSD or under APFS, and until the system reuses them the old bytes may be recoverable from the disk. The history that is sealed now is safe from the next write on; what a disk already held is not made unreadable by this. Images pasted into a terminal are the one plaintext the history makes: a terminal reads a path, so the PNG is written to a private folder (`0600`, swept at launch and quit) and is removed after a few pastes. The draft in flight (the words of a draft you are still speaking, kept so that a crash costs half a second) is sealed under the same key; while the history is paused it is not written, so a crash during a draft in that state recovers nothing.

### The state file, sealed

`state.json` held your saved addresses (breaths, with the window titles and URLs in them), the windows Lodestar has parked, how often you use each app, the meetings you have joined or dismissed, and how far the walk has got. It is now `~/.local/share/lodestar/state.sealed`, with its last-known-good copy `state.sealed.bak`, encrypted under a fourth key, the `state` ring in the same login keychain. It has a ring of its own because deleting the logbook destroys the logbook's key, and the breaths must not go with it.

- **Your state from before this version** is taken in at the first launch: the plaintext `state.json` is read, written sealed, read back and compared byte for byte, and only then removed, together with its plaintext `.bak`, which becomes a sealed backup. Interrupted at any moment, the next launch does it again. A `state.json` that does not parse is moved aside as `state.json.corrupt-<time>`, never deleted, and the backup is tried.
- **A build older than this one** that you run again finds no `state.json` and starts with an empty state (it does not know the sealed name, on purpose, so it cannot misread it), and writes a plaintext `state.json` of its own. The next launch of this version merges that file in and removes it: breaths by address (the older build's copy of an address replaces the sealed one, because it started from nothing and so holds the later answer), usage by the larger count and the later time, spent meetings together, the walk, the curriculum and the editor's consent from whichever side has them. A lesson you completed stays completed. Merging the same file twice changes nothing, so a launch cut short is simply run again. What the older build could not do is carry the sealed state forward: during the time it ran, `state.sealed` was not updated.
- **When the keychain cannot be asked** (locked, or it refused): the state is paused for the launch. Nothing is read, written, removed or taken in, and the plaintext (if there still is any) is left as it is. Lodestar runs on an empty state held in memory and says so in a flash; because the walk, the editor's consent and the coach's lessons live in the state, none of them is shown or asked while it is unknown, rather than asked again from scratch. What you change meanwhile (a breath saved, a window parked) is kept in memory and never written in the clear. When the keychain answers (the screen unlocking, if it was only locked) the state is read and what changed is merged into it; a breath you deleted meanwhile stays deleted. If it never answers, those changes are lost at quit, and the next launch starts from what the disk holds.
- **When the key is gone** (a restore without the keychain, the item deleted in Keychain Access) and a sealed state exists: it cannot be read, so it is moved, never deleted, into `state-unreadable-YYYY-MM-DD/`, a new key is made, the state starts fresh, and you are told once (a flash, the log, `lodestar diagnose`). A plaintext `state.json` beside it, if there is one, is taken in.
- **When the file is damaged** (altered, torn): a copy is kept as `state.sealed.corrupt-<time>`, the backup is restored, and you are told. A `state.sealed` that has gone missing beside its backup is restored from the backup.
- `lodestar diagnose` says whether the state is sealed, whether its key is there, and what the state holds. The command line reads it without changing anything: it never makes a key, takes a backup or merges.

The state is saved as often as before (every summon touches the frecency, every park the parking record), on the same thread and with the same single atomic write: sealing adds microseconds of encryption to a write that costs milliseconds of disk, and the file is smaller (it is no longer pretty-printed).

`lodestar uninstall` keeps all four keys, because the sealed data it keeps is unreadable without them; `lodestar uninstall --purge` stops a running Lodestar first (it saves on its way out, and would put sealed files back), removes the data, and then deletes the keys (service `com.vaccone.lodestar`, accounts `lodestar.ring.health`, `.logbook`, `.clipboard` and `.state`) from the login keychain. A key the keychain would not delete is named, the rest of the uninstall still runs, and the command exits 1.

## The coach

Once the observations have something worth saying, the coach says it: one suggestion at a time, in a small glass chip after a navigation, priced in your own numbers — "you searched for it 31 times this month · about 40 seconds a week". It never interrupts a meeting (a live camera silences it), never takes focus, and never captures a key your typing could want.

Its whole grammar lives on the lode key. **Tap lode twice** to accept: the coach writes exactly one config line — a graph binding, a route, a retirement — through the same path ⌘K uses, and flashes the receipt. **Lode ⌫** means not this one; the suggestion sleeps for a season and returns only if the evidence keeps growing. **Ignoring it** is also an answer: the chip fades on its own, the offer parks in the menu bar as an inbox of at most one, and it may try again at a better moment, a couple of times, before parking quietly.

The first weeks are different. The first launch asks which door you came for, Write, Switch, Keep or Speak, and walks that one door to a real success, and stops; the rest of Lodestar arrives one lesson at a time, in Lodestar's own voice on the same card, the keys it teaches drawn beneath — the launcher and the editor first, for whoever did not choose Switch or Write, hints on the second day, Ask on the fourth, then the draft, select, commands, scroll, the clipboard, and last the sheet — each only if you have not found the gesture yourself, each proved by doing it once. **Lode ⌫** on a lesson means later; it returns once, days on, then parks. The coach paces itself by what your hands demonstrate, not by a calendar: after you accept a new address it stays silent until that address has actually compiled into your fingers, then considers the next. Expect it to speak rarely — a suggestion or two a month at most — and to say nothing at all for the first weeks while the evidence accrues. `coach.enabled` set to false turns the whole voice off; the findings remain readable in `lodestar observations` either way.

## Settings (`lode ,`)

Settings opens on its overview: ten places on a ring around the Lodestar mark, each with its picture and one line saying what that part of Lodestar is doing. A dot beside a name means something there needs you. Every option the config file holds is in one of the places, and nothing else is — the window and the file cannot drift in either direction, and a test enforces it.

**Digits open places, from anywhere:** 0 General, 1 Write, 2 Switch, 3 Keep, 4 Speak, 5 Operate, 6 Web, 7 Meetings, 8 Keys, 9 Observations. **Letters act on rows**, each fixed to its row so the hand can learn them; where a place has one switch for all of it, that switch is `a`. `/` searches every row, including the words you would use for a place ("clipboard", "dictation"), and each hit shows the two keys that reach it. **Escape steps back one level** — a page to its place, a place to the overview, the overview to closed. `lode ,` opens the place for whatever is in front of you: over the strip, Keep; over the draft, Speak; over the editor's marks, Write; over Ask, Web. A search lands on its row and lights it with a border in the accent; return then works the row. On macOS 26 with Apple Intelligence on, you can ask in your own words ("make scrolling slower") and Apple's on-device model suggests the row. **⌘Z undoes the window's last change** and ⇧⌘Z redoes it; **History** (General, then h) lists every recent change from Settings, the file, the coach or the editor, each with Undo. Tab walks every control; **return is the only commit** — a field left any other way snaps back to what the file says. Inside a list, arrows select, return edits, delete removes, and `a` jumps to the add line.

A value you set wears a dot and a Reset beside it; a value Lodestar chose says so, as Automatic or System with what it picked. Permissions live with what needs them (Accessibility in General, Screen Recording in Operate, Calendar access in Meetings) and open the right pane of System Settings when they are not granted. Deleting the logbook, the health record or Keep's history asks for its letter twice. The doctor's findings render beside the rows that fix them. One deliberate exception: the graph is edited where addressing happens — ⌘K and the file — never in a place.

## Config (`lodestar.json`)

The config is sparse JSON: it holds only what differs from the defaults,
so the file reads as pure intent. Every option's documentation lives in
the schema (editors surface it as you type; `lodestar schema` prints it),
and every writer — a hand edit, ⌘K in the launcher or in Ask,
`lodestar config set` — converges on the same canonical bytes.

```json
{
  "$schema": "lodestar-schema.json",
  "version": "0.24.3",
  "web": {
    "links": { "yt": { "url": "youtube.com", "profile": "brave:Google" } },
    "routes": { "acme": "brave:Work" }
  }
}
```

The `graph` section holds your letters: nested letters are the trie; values are an app name or `<browser>:<profile name>` (`brave:Work`, `chrome:Personal`). **Multi-letter keys are sugar**: `"eo": "Outlook"` binds the chain E → O without writing the nesting (any depth: `wgg` works); a multi-letter key whose prefix is already a destination is refused with a validation problem. **Disabling** (the `gestures` section) gives every gesture a named switch — `"scroll": false` frees its keys to pass through to the app, shift variants included. Reserved first letters: `O`, `Z`, `X`. Breaths live on `'`, vim's mark key for a saved position, so M is Messages and B is free to bind. Deleting a key restores its default; `lodestar config` prints the full effective picture. Menu bar → Reload Config applies edits and reports every validation problem.

**Migrating from 0.9.9 and earlier**: the automatic `lodestar.yaml` →
`lodestar.json` conversion ran from 0.9.10 and is now retired. If a
`lodestar.yaml` is still sitting in `~/.config/lodestar`, nothing reads
it — the JSON beside it is the config, and the stale file is safe to
delete. Upgrading from 0.9.9 or earlier now starts from defaults, so copy
the settings across by hand (or install 0.17.0 first and let it convert).

**Shift always means something** (beside, bind). If a hyper key shim rewrites right ⌘, configure it to exclude shift from its output — Lodestar accepts both the raw right-⌘ device bit and the shim's `⌘⌃⌥` form.

## Controls & state

- Menu bar star: How Lodestar Works · Settings · Check for Updates · Send Feedback · a parked coach suggestion when there is one · Quit Lodestar (quitting restores everything parked) · Uninstall Lodestar. Verbs only — preferences live in Settings, and the watched config makes a reload item redundant. Send Feedback writes a note in Lodestar's own window that reaches its maker by email; a reply address and the diagnostic report are both optional, and the report can be read before it is sent. Hide it with `app.show-menu-bar: false` — then picking **Lodestar** in the launcher reveals it for 60 seconds with the menu popped open, ready to use. (Hidden mode forgoes the chain-active star; the guide panel still shows every pending chain.) `kill -USR2 $(cat ~/.config/lodestar/lodestar.pid)` reloads the config from scripts.
- CLI: `lodestar check [--json]` validates the config (schema + referential + ground truth); `lodestar reload` applies it to the running instance; `lodestar config` prints the effective config, `config get <path>` one value, `config set <path> <value>` a validated write applied live, `config unset <path>` the way back to default; `lodestar diagnose` prints one paste-able report (version, instance, trust, displays, config, state, log tail); `lodestar schema` and `lodestar config-path` serve tools and agents — see AGENTS.md for the agent contract.
- `scripts/install-app.sh` — build, sign, and install `~/Applications/lodestar.app` with a login LaunchAgent, so Lodestar survives reboots. **First install**: grant the app Accessibility when it prompts (System Settings → Privacy & Security → Accessibility) — Lodestar wakes up on its own within seconds of the grant. Signed with your Apple Development identity, so the grant survives rebuilds.
- `scripts/dev-restart.sh` — rebuild + hot-swap (unloads the login agent so launchd doesn't fight the dev instance).
- State: `~/.local/share/lodestar/state.sealed` (breaths, parked frames, usage; sealed, see "The state file, sealed") — **versioned and self-defending**: every boot keeps a last-known-good `state.sealed.bak`; a corrupted file is quarantined with a timestamp, restored from backup, and announced in a flash — never silently reset. Old formats migrate on load. Log: `~/.local/share/lodestar/lodestar.log`. Config and the pid file stay in `~/.config/lodestar`; everything Lodestar accumulates lives in `~/.local/share/lodestar`, which is deliberate — `~/.config` is what people commit to dotfiles repositories. `kill -USR1 $(cat ~/.config/lodestar/lodestar.pid)` dumps diagnostics to the log.
- Versions: the binary knows its version (`lodestar 0.9.0 starting` in the log, shown in the menu header), and both the state file and `lodestar.json` record the release that wrote them — schema changes migrate the file at boot, with the writing release always on record.

## Config DX

- **Every reload validates everything**: JSON syntax, unknown keys with "did you mean" hints, types/enums/ranges, profile references against each browser's real profile list, and app names against what's installed. Problems flash on screen and land in the log. `lodestar config set` refuses any write that would introduce a problem.
- **Editor intelligence for free**: the config's `$schema` key points at `lodestar-schema.json` (emitted beside the config, generated from the same typed schema (`ConfigFile.schema`) that validates reloads — they cannot drift). VS Code natively, and any LSP-aware editor, gets completion, hover docs, and type checking.
- **The file is watched, always**: saving applies the config the moment it parses, and a file that does not parse is announced once and left un-applied — the running config stays the last good one. Saving is validating; there is no switch.
- **`app.start-at-login`** (default true) — the installed app installs or removes its own LaunchAgent to match; setting false never kills the running session, it just stops the next login from starting one. Dev builds never touch login items.
- **`app.auto-update`** (default true) — the installed app keeps itself current: a daily check, a background download, and a strict verification (signature integrity, this team's Developer ID, this bundle id, version matching the release) before anything moves. The swap waits for a quiet moment — no chain, no panel, ten minutes since the last gesture — hands the session over exactly like a manual reinstall, and a watchdog restores the previous version if the new one fails to boot. One flash afterward: quiet, never hidden. Menu bar → Check for Updates… checks and applies immediately. Dev builds never self-update.
- **`app.channel`** (default `stable`) — which releases the updater follows. Every build ships to `preview` the moment it is published. `stable` takes a build once its line has run on preview Macs for a while: a new minor version after seven days, patches to the stable version after three, and never a build less than a day old, so a run of daily patches can delay nothing. The website decides stable (`lodestar.vaccone.software/api/stable`) and is the only place the rule lives, so changing it is a site deploy; the app, the Homebrew cask and the download button all read that one answer. The app believes it only when it names one of Lodestar's own releases on GitHub, and the download must still carry Lodestar's Developer ID, so a wrong answer can hold an update back but never install anything else. A build found bad is held (`scripts/hold.sh`) and its line waits for the next one; a fix that should not wait is marked a hotfix (`scripts/hotfix.sh`) and is stable at once. Switching from preview to stable while ahead stays on the newer build until stable passes it; the updater never moves backwards. `scripts/channel.sh` shows where both stand.
- **`lodestar --check`** — full validation from the CLI, exit code included: `~/Applications/lodestar.app/Contents/MacOS/lodestar --check`.
- **`keys:`** overlays the key-name table (`keycode: name`) — the user's last word. Beneath it the table already follows your keyboard: a fully ASCII layout (Dvorak, Colemak) is adopted wholesale so every label, chain letter, and gesture names the printed keycap; a layout with a few non-ASCII keys adopts its letters and digits; anything that cannot keep the name set coherent behaves as ANSI always has. Recomputed the moment the input source changes.
- **Crash self-healing**: the LaunchAgent restarts Lodestar after a crash (10s throttle) but never after a clean Quit.
- **Every letter belongs to the graph.** As of 0.17 no letter is reserved: orientation moved to `\` in 0.14.2, the attention timeline was retired, and layout undo moved to `lode ←` / `lode →`, where walking a history is what the arrows already mean. A verb that sits on a letter costs an address forever, and an address is the scarcer thing.
- Menu harvesting and scroll-pane discovery run off the main thread — a hung app can no longer freeze Lodestar's UI; the panel opens instantly and rows arrive when ready.
- **Logs are logfmt** (`15:04 INFO summon target=Slack candidates=[8688]`) — greppable and machine-parseable — rotating at 5MB with two predecessors kept (`.1`, `.2`), bounded ~15MB, history preserved.
